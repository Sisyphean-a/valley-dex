# 玩家优先图鉴恢复总纲

> **新会话第一入口。** 任何继续 schema 5 迁移、修复当前 App、恢复可用版本或验收真实数据包的工作，都先完整读取本文件，再按本文指针读取相关决策。当前 `master` 能安装 schema 5 包，但玩家界面不合格，**不是发布候选，也不是路线图完成状态**。

- `E:\github\valley-dex`
- `E:\github\stardew-offline-data-builder`

先保全当前工作，再恢复一个可运行的 schema 4 成品线；随后保留合格的 schema 5 基础设施，重做 builder 玩家事实投影、App 分类展示和真实验收。不要从零重写两个仓库，也不要继续在当前通用事实表格上堆补丁。

### 当前产品故障

真实设备截图已证明当前 schema 5 玩家界面存在以下发布阻断问题：

1. 首页和分类页直接显示 `crop`、`quest`、`big_craftable`、`villager` 等内部类型名；
2. 村民卡片以巨大图片、中文名和英文名占满空间，没有生日、常住地等行动摘要；
3. 多张人物头像被错误裁切，只显示半张脸；
4. 详情直接显示 `Fall 11`、`Female`、`direct`、`derived` 等英文枚举和技术词；
5. `Data/Characters.json`、证据类型、版本号和转换规则被重复拼进每一条“核心信息”；
6. 礼物偏好泄露 `Oh`、`you're` 等未解析英文 token 和未解析引用；
7. 同类事实被拆成大量重复行，核心答案难以扫描；
8. 人物详情没有按“常住地/日程 → 生日/最爱礼物 → 婚配资格/关系”组织；
9. 所谓真实包验收只证明“可安装、分类非空、标题非空”，没有证明中文、信息层级、图片或玩家任务正确。

这些故障违反既有决策，不是用户要求。尤其违反：

## 根因

### 实现根因

当前 `Schema5WikiCatalogue` 把数据库事实直接压平成通用 `label/value`：

- `factRows()` 把来源描述拼入每个玩家事实；
- `sourceDescription()`输出文件、版本、证据和转换细节；
- 未知槽名通过替换下划线直接进入 UI；
- `Schema5TypedValue.display()`只做底层字符串转换，不做玩家语义本地化；
- 所有事实进入同一个“核心信息”，没有分类专属排序和模块；
- 未解析礼物引用仍可显示；
- manifest `displayName` 未通过中文玩家标签门禁；
- App 继续用旧通用详情组件承载新契约，没有实现四层详情。

### 验收根因

`RealV5PackageAcceptanceTest` 当前只检查：

- 包能安装；
- 分类和条目非空；
- 详情标题非空。

它没有执行决策 12 的真实玩家任务，也没有断言技术字段零泄露、未解析引用为零、行动摘要完整、图片正确或首屏有效。因此“数据库能打开”被误报成“产品可用”。

### 规划结论

现有 13 个决策的产品方向总体正确，不需要推翻。需要补上的执行纪律是：

- 分类黄金样本必须早于批量接 UI；
- 玩家界面技术词零泄露是自动阻断项；
- 未解析引用和未本地化枚举是包或投影失败，不是可显示内容；
- 真实截图和玩家任务必须早于发布声明；
- 决策关闭表示设计已确定，不表示代码已经完成。

## 恢复策略

采用“双线止损 + 纵向替换”，不做全仓重写。

### 先保全，再恢复

执行前：

1. 重新检查两仓 `git status --short`、当前分支和 HEAD；
2. 为 App 当前 HEAD 和 builder 当前 HEAD 建立不会移动的备份 ref；
3. 从 App `54acb84` 建立独立 schema 4 恢复分支或 worktree；
4. 使用 builder 的 `build-v4-legacy` 或冻结的已验证 v4 包恢复可用内容；
5. 运行 schema 4 最窄自动检查并在设备上走首页、分类、详情、搜索、收藏和返回；
6. 未证明恢复线可用前，不删除当前 schema 5 分支、不重写历史、不移动远端主分支。

**完成标准**：存在一个可复现、可安装、可浏览的 schema 4 恢复版本；当前 schema 5 工作完整保留；两者互不覆盖数据目录和 Git 历史。

### 保留的 schema 5 工作

以下基础设施原则上保留并补测试，不因 UI 失败而重写：

- manifest 2 / schema 5 / `player-facts-v1` 表结构；
- 类型化 SQLite repository 和绑定查询；
- schema 指纹、hash、索引、`quick_check`、`foreign_key_check` 和语义验证框架；
- staging、原子激活、失败保持原包；
- `active_v5`、`previous_compatible_v5`、`pinned_legacy_v4` 生命周期；
- 稳定 ID、事实状态、条件、证据、关系和视觉记录；
- 数据库侧搜索、facet、反向关系和游标分页基础。

“原则上保留”不等于默认正确。每个模块仍需通过当前契约测试；发现语义错误时局部修复。

### 必须重做的工作

以下部分不能继续沿用当前通用展示方案：

- builder 的玩家可读中文事实和值归一化；
- `entity_cards` 的分类行动摘要；
- 礼物、材料、产物、掉落和关系引用解析；
- 分类中文名称和受控搜索语义；
- 人物及其他异常图片的取图、裁切与人工复核；
- `Schema5WikiCatalogue` 的分类专属展示投影；
- `WikiEntry`/详情模型对立即行动、完整资料和数据说明的明确分层；
- 当前通用 `label/value` 核心信息表格；
- 真实包验收、截图验收和八类玩家任务。

## 执行顺序

### R0：恢复可用成品

完成“先保全，再恢复”的六项工作。schema 4 恢复线是止损版本，不是 schema 5 的长期双写或运行时回退。

**证据**：备份 ref、恢复分支、构建/测试结果、设备关键路径截图和使用的数据包 hash。

### R1：先建立红色产品门禁

在修 UI 前增加能稳定复现当前故障的测试和检查：

- 玩家默认界面禁止出现内部类型名、原始路径、内部 ID、证据类型和转换规则；
- 玩家事实禁止出现未本地化枚举；
- `未解析引用`、残缺英文 token 和不可解析目标数量必须为 0；
- 所有可浏览 manifest 类型具有经批准的中文名称；
- 每个分类代表卡有契约要求的 1–2 条行动摘要；
- 数据说明只允许玩家文案，如“依据游戏数据整理”“条件依赖游戏进度”；
- 原始路径、locator、原始条件和转换规则只允许出现在独立诊断数据，不进入普通 `WikiEntry`；
- 真实包验收逐项执行玩家任务，不得只断言非空。

先让这些测试在当前 schema 5 实现上失败，再开始修复。

**完成标准**：当前截图中的每类故障都有至少一个失败断言；测试失败信息能指出实体、槽和泄露值。

### R2：乔迪纵向黄金样本

先只打通一个真实村民，不批量修 34 个村民，也不先做八类通用渲染器。

乔迪样本必须达到：

- 列表卡显示正确、完整、可辨认的人物头像；
- 默认只显示中文名，不用英文名占卡片空间；英文名可保留给搜索或次级别名；
- 卡片两条摘要为中文生日和有证据的常住信息；
- `Fall 11` 归一化为“秋季 11 日”；
- `Female` 不进入核心答案；确有玩家价值时显示“女性”，否则隐藏；
- 详情立即行动区按人物契约展示 3–6 个答案；
- 最爱礼物解析为可点击中文实体，不显示 raw token、ID 或未解析文本；
- 完整礼物和日程进入可展开资料；
- 数据说明不重复铺满每一行，普通官方固定事实不显示来源徽章；
- 技术 provenance 保留在数据库和诊断入口，不进入普通详情；
- 360×800 首屏可看到身份和至少三个有效核心答案；
- 320×568、fontScale 2.0 下无需滚动可看到第一个核心答案；
- TalkBack 朗读中文名称、状态和行动摘要。

builder、fixture、`WikiCatalogue`、Compose、自动测试和真实设备截图必须一起完成，任何一层缺失都不算样本完成。

**完成标准**：用户仅看列表和详情截图就能回答“她住哪里、生日何时、最爱什么、能否婚配”，且页面没有技术泄露和错误裁切。

### R3：完成村民类别

以乔迪样本为固定黄金输出，扩展全部村民：

- 中文生日、常住地、日程规则、礼物五档、婚配资格和有向关系；
- 文森特和贾斯只显示“亲友关联（具体关系未注明）”；
- `LoveInterest` 不表示当前恋爱；
- 所有画像通过代表样本和异常图人工复核；
- 长名称、无数据、条件化、未知和未收录状态均有样本。

**完成标准**：34 个村民中技术词和未解析引用为 0；核心槽覆盖达到决策 12；固定截图样本全部通过。

### R4：按玩家任务逐类替换

按以下波次完成 builder + App 纵向能力，每一波通过后再开始下一波：

1. 商店与作物：地点、时间、购买/兑换、季节、成熟、种子来源、售价；
2. 大型可制作物与工具：用途、材料、制作/加工、完整升级链；
3. 怪物、鱼和武器：出现区域/矿井层段、掉落、水域/捕获条件、伤害和获得方式；
4. 其余可浏览类型：先定义对玩家有价值的契约；没有契约的内部类型不得直接作为英文分类上线。

每类都必须拥有：

- 真实代表实体；
- 中文卡片行动摘要；
- 分类专属立即行动顺序；
- 完整资料折叠结构；
- 状态、条件、关系和图片异常样本；
- 列表、详情、搜索/facet/反查任务；
- 真实截图与自动黄金输出。

**完成标准**：一类通过完整玩家任务后才有发布资格；“数据库里有记录”不算完成。

### R5：真实 v5 联合发布验收

全部分类完成后，执行决策 12，不得缩减为安装检查：

- 真实资产构建及包 hash；
- 逐分类/逐核心槽覆盖；
- 条件、关系、facet、搜索和视觉审计；
- 图片人工复核，`pending_review=0`；
- API、屏幕、字体、深浅色和 TalkBack 矩阵；
- 八类玩家任务及错误/空状态；
- 性能 SLO、查询计划、分页和切包回滚；
- 与冻结 v4 或上一获准 v5 的差异；
- 具名 release attestation。

**完成标准**：所有硬门禁通过、截图经人工确认、用户认可真实代表页面后，schema 5 才能替代恢复线成为成品。

## 玩家界面硬门禁

普通页面出现以下任一内容即失败：

- 英文内部类型名或未经批准的英文分类名；
- 原始文件路径、JSON path、record key、claim/evidence ID；
- `direct`、`derived`、转换规则名、内部 predicate、slot key；
- `Fall`、`Female` 等未翻译枚举；
- `未解析引用`、残缺句子、孤立 token 或原始实体 ID；
- 用类别名、记录数、商品数等低价值信息填补行动摘要；
- 同一来源说明重复在每条事实后；
- 把动态、未知或暂未收录显示成固定事实；
- 把图片损坏显示成普通无图；
- 错实体、半张脸、不可辨认主体或未经说明的代理图。

普通页面允许的来源表达仅限玩家可理解的结论，例如：

- “依据游戏数据整理”；
- “依据游戏数据计算”；
- “受游戏条件限制”；
- “当前数据包暂未收录”；
- “官方资料不足，暂时未知”。

详细来源、版本、路径、定位器和转换链进入独立诊断界面或发布报告。

## 实现边界

- builder 拥有事实语义、中文规范值、关系、条件、provenance、图片绑定、卡片和 facet 投影；
- App `WikiCatalogue` 拥有玩家信息层级、分类排序、简短状态文案和页面 DTO；
- Compose 只渲染明确层级，不从 slot key、label 或非空值猜优先级；
- App 不修补 builder 的英文枚举和未解析引用；此类输入应被 builder 门禁拒绝；
- App 不读取 `extra_json`、`officialDerived` 或 `legacyFields`；
- schema 4 仅作为恢复版本和迁移基线，不成为 schema 5 的运行时 fallback；
- 真实资产、`.svdata`、截图和中间报告放仓库外或根 `.tmp/`，不得成为 Git 跟踪源码依赖。

## 验证要求

每个切片至少执行与风险匹配的最窄检查；跨 builder/App 的切片必须同时验证两仓。开始前从当前配置确认命令，通常包括：

- builder：`pytest`、`ruff check .`，以及对应 schema 5 fixture/真实候选命令；
- App：`testDebugUnitTest`、`lintDebug`、`assembleDebug`、`assembleDebugAndroidTest`；
- 设备：目标 instrumentation 测试、真实页面截图、TalkBack 和关键路径人工操作；
- 两仓：`git diff --check`。

不得用合成 fixture、单一 API 模拟器、标题非空、构建成功或数据库可打开代替真实发布验收。

## 每轮工作协议

新会话按以下方式持续推进：

1. 先读本文及当前切片链接的决策；
2. 检查两个仓库工作树，保留所有用户改动；
3. 一次只认领一个可独立验证的纵向切片；
4. 修改前先建立失败测试或可复现截图；
5. 同时修 builder 输出、App 投影和页面，不在错误层做字符串遮盖；
6. 运行最窄检查，再扩大到跨仓库和设备验证；
7. 实际观察截图，发现英文泄露、低密度、错误裁切或层级错误就继续修；
8. 记录当前证据和残余风险；
9. 切片完成后再进入下一个，不把检查点称为最终成果。

遇到真实资产、实体设备或人工图片复核不可用时，先完成所有不依赖外部动作的工作，然后准确说明所需路径、设备或审核，不伪造通过。

## 权威资料顺序

发生冲突时按以下顺序判断：

1. 用户最新明确要求及本文的恢复状态；
2. 两仓库当前代码和已接受 `.codestable` 当前态；
3. [路线图总览](map.md)和 13 个已关闭决策；
4. 历史提交和旧测试。

本文只修正“实现状态被误判为完成”和恢复顺序，不推翻 01–13 的领域契约。详细语义只在对应决策维护，本文通过链接引用。

## 禁止的捷径

- 不从零重写两个仓库；
- 不直接重置、强推或删除当前 schema 5 历史；
- 不在 App 用字符串替换掩盖 builder 错误；
- 不恢复 `officialDerived` 或 raw JSON 作为 schema 5 回退；
- 不先批量铺开八类再做一个真实黄金样本；
- 不把 provenance 全塞进普通详情以证明“有来源”；
- 不把真实包能安装称为玩家验收完成；
- 不在没有真实截图检查时宣称 UI 完成。

## 最终完成定义

只有同时满足以下条件，恢复工作才完成：

- 存在经过验证的可用恢复版本，迁移期间玩家不被迫使用坏 UI；
- schema 5 基础设施保留且通过契约验证；
- 八类核心页面全部中文、任务优先、信息密度合理；
- 技术字段和未解析引用在玩家界面为 0；
- 图片正确、完整、可辨认；
- 搜索、facet、反查、状态和条件语义正确；
- 决策 12 的真实包、设备、玩家任务、性能和回滚证据完整；
- 用户审阅代表性真实截图并认可后，才将 schema 5 标记为成品。
