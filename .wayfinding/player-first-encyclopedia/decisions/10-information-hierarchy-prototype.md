# 玩家信息层级原型

## 问题

哪种低成本列表与详情原型能让代表性新手、普通和资深任务快速找到首要答案，同时把次级机制渐进展开、把技术字段留在玩家界面之外？

## 答案

### 原型结论

采用“响应式实体列表 + 四层详情”的低成本结构原型。各类别共享阅读层级，但核心答案的内容和顺序由分类契约决定；UI 不根据字段标签、底层表或事实/关系数据类型重新猜层级。

### 列表密度

- 首页“全部分类”的分类入口继续使用四列网格；分类入口不是实体条目。
- 实体列表在手机上默认两列；极窄屏或 2.0 倍字体下允许自动降为单列；平板按最小可读卡宽增加列数。
- 实体卡显示视觉、名称和最多两组短行动摘要。摘要来自 schema 5 的 `entity_cards`，不是页面临时拼接。
- 没有可靠核心摘要时宁可少显示；类别名、店主、商品数、记录数和技术参数不得补位。
- TalkBack 必须完整朗读名称、事实状态和最多两项摘要，不受视觉截断影响；点击语义区域不小于 48×48dp。

固定四列实体卡被否决：320dp 屏幕下每卡约 66dp、扣除内边距后文字区约 46dp；360dp 下每卡约 76dp、文字区约 56dp，无法在字体放大时可靠表达名称与两组行动摘要。

### 详情四层结构

1. **身份头部**：实体视觉、名称、可选英文名和一句话用途/辨认说明。类别标签等不能帮助行动的信息不抢占头部。
2. **立即行动**：按类别顺序展示 3–6 个核心答案。事实、关系、报价、材料和地点可以混合编排，不能因底层数据类型不同而被推后。条件紧邻所限制答案；未知、暂未收录和不适用占住合同位置，不静默消失。
3. **完整资料**：材料全集、全部报价、完整日程、五档礼物、完整关系、掉落表、机器规则和深度机制。每组先给可读概括，再由玩家展开；标题说明内容，不只显示“若干项”。
4. **数据说明**：玩家可理解的条件限制、未知原因、来源类别、适用版本和“依据游戏数据整理/计算”。原始文件路径、定位器、转换细节和不透明条件原文只进入诊断界面。

默认层与展开层由 `WikiCatalogue` 的类型化展示投影明确给出；Compose 不通过中文标签、值是否为空或记录类型决定优先级。状态、条件摘要和来源提示是事实展示模型的一部分。

### 八类代表原型

| 类别 | 实体卡行动摘要 | 立即行动区顺序 | 完整资料默认折叠 |
|---|---|---|---|
| 商店 | 地点；营业/出现时间 | 地点与营业/出现规则 → 商品报价、兑换成本与条件 | 完整商品、库存/限购、随机规则、价格修正、货币、店主和闭店例外 |
| 作物 | 季节；首次成熟，必要时再生 | 季节与成熟 → 种子来源和成本 → 收获/再生/关键要求 → 出售价格 | 生长阶段、产量、品质、肥料/职业、收益推演和用途 |
| 村民 | 生日；常住地点 | 常住地和日程适用规则 → 生日与最爱礼物 → 婚配资格与有证据关系 | 完整日程、五档礼物、关系组、婚后和特殊日程；角色配对指针不冒充当前恋爱 |
| 大型可制作物 | 一句话用途/主要产物；解锁阶段 | 用途 → 制作条件或其他获得方式 → 加工/容量/放置规则 | 材料全集、完整机器规则、条件产出、购买来源、反向用途和少见限制；按机器、设施/容器、装饰/照明、不可制作物选择有意义模块 |
| 工具 | 工具类型；档位或主要提升 | 用途与档位 → 前一级、材料、购买价、办理地点和解锁条件 → 升级耗时与效果 | 附魔/锻造、附件、特殊取得、出售和丢失规则 |
| 怪物 | 出现区域/矿井层段；主要掉落 | 去哪找 → 掉落 → 生命/攻击 → 自然语言战斗特征 | 完整掉落、经验、速度、韧性、变体和深度机制 |
| 鱼类 | 水域/地点；季节/时间窗 | 去哪钓 → 季节、时间、天气 → 特殊条件 → 出售价格 | 难度/行为、概率、离岸距离、尺寸、经验、鱼塘和用途 |
| 武器 | 类型/伤害；主要获得方式 | 怎么获得及具体地点/矿井层 → 伤害和类型 → 购买/兑换与出售价格 | 速度、击退、精准、防御、范围、暴击、库存和丢失规则 |

### 状态与异常样本

- 核心位置覆盖 `fixed`、`conditional`、`dynamic_rule`、`unknown`、`not_collected`、`not_applicable`；部分识别条件同时显示已解释部分和“另有未识别条件，需在游戏中确认”，完全不透明条件显示“受游戏条件限制”。
- 官方无图、合法代理视觉与数据包缺图/解码失败使用不同展示状态；错误状态不能伪装成正常占位。
- 长名称、无图、长条件、多报价/多材料/多关系和核心事实缺失均作为压力样本。
- 原始 ID、枚举、哨兵值、规则数量、纹理字段、`MineBaseLevel`、裸 AI 参数和原始条件不进入默认或完整玩家资料；需要排障时只进入诊断层。

### 原型验证基线

- 视口覆盖 320×568、360×800、393×873、411×891dp；字体倍率覆盖 1.0、1.3、2.0。
- 无横向滚动、控件重叠或越界裁切；响应式列数不牺牲卡片可读性。
- 360dp / 1.0 下，代表卡片无需进详情即可辨认名称和两组短行动摘要；320dp / 2.0 下 TalkBack 仍完整播报。
- 360×800dp / 1.0 下首屏看到身份头部和至少前三个核心答案；320×568dp / 2.0 下无需滚动即可看到第一个核心答案。
- 八类各有一个正常代表样本，并覆盖长名称、无图、长摘要、大集合、核心事实缺失和全部事实状态。
- 展开/收起后焦点和滚动位置稳定；旋转或状态恢复后折叠状态保持。
- 默认界面不得出现技术枚举、内部 ID、原始条件或错误的关系推断。

### 范围边界

本原型确认信息结构、响应式密度、投影职责和可检查行为，不锁定颜色、形状、动画、最终 Compose 组件、精确文案或 schema 5 的物理列名。搜索排序和浏览 facet 组合由决策 11负责；最终门槛、样本规模和设备证据由决策 12负责。

## 依据

- 用户在 2026-08-13 接受响应式实体列表、详情四层结构、八类代表首屏和验证基线。
- [分类信息契约](04-category-information-contracts.md)已确认八类核心问题，[人物关系模型](05-character-relationship-model.md)限制关系推断，[条件与来源可信度](06-condition-and-provenance.md)要求状态、条件和来源邻近表达，[跨仓库数据契约](09-cross-repo-data-contract.md)提供 `entity_cards`、事实槽和类型化展示输入。
- 当前 `WikiEntrySummary` 除商店专用结构外没有行动摘要；`WikiEntryGridItem` 只显示图片、名称、英文名和类别/店主商品数，无法满足分类契约。
- 当前 `WikiCatalogue.entrySections` 把事实统一合并为“核心信息”，`DetailScreen` 固定按 sections → submenus → relations 排列，导致地点、报价、材料或获得关系可能被底层类型推迟。
- 当前 `EntryFact` 只有 label/value，不能表达事实状态、条件完整性、来源提示或展示优先级；schema 5 实施必须由类型化投影补齐，不能让 UI 按字符串猜测。
- 三路独立只读评审分别覆盖八类任务流、Android 小屏/字体密度和条件/关系/大集合对抗场景，结论一致：固定四列实体卡不可读，详情必须按玩家行动而非存储类型排序。
